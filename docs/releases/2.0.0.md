# @velve/auth 2.0.0

## Summary

2.0.0 is a security release and a major version. It answers an audit of the
security requirements that found fourteen the code did not, or only partly,
satisfied (E-2091), and the follow-ups that audit led to. Every installation
should upgrade.

It was prepared as 1.2.0, a minor version by the owner's decision (E-2214,
E-2520), and never published under that number. Some of its changes can stop an
existing installation from starting or an existing caller from compiling, so it
ships as 2.0.0, honest under semver, and the major also removes what a minor
could not: three subpaths that never exported anything and `user.findByEmail`
in identity mode `username` (E-3020). **1.x gets no further releases.** The
security fixes below reach an installation on 1.1.0 only through this version.

Read *Breaking changes* and *Upgrading from 1.x* before upgrading. The sections
after them describe each change in full.

## Breaking changes

Every change in this release that can stop an existing installation from
starting, stop existing code from compiling, or make an existing call answer
differently. Each one is described in full in the section named after it.

**Removed**

- `@velve/auth/postgres-js`, `@velve/auth/neon` and `@velve/auth/import` are
  removed. They exported nothing; an import of any of them no longer resolves
  (E-2902, E-3021).
- `auth.user.findByEmail` is removed in identity mode `username`, on the type
  and on the object. Use `findByUsername` there (E-2834, E-3022). It stays in
  `email` and `username_email`.

**Refused at start** (*Upgrade notes* > *Five new `VelveStartupError` codes* and
*Other refusals at start*)

- A plugin route without a usable `perIpAddress` bucket:
  `plugin_route_without_address_rate_limit` (E-2214).
- `rateLimit.perIpAddress` or `perAccount` given as something other than a
  real bucket, `"none"` from JavaScript for instance: `rate_limit_bucket_unusable`
  (E-2215).
- A plugin migration whose `createsTables` names a table that is not a plain
  identifier: `plugin_migration_table_not_an_identifier` (E-2481).
- Argon2id `memoryKiB` above 1048576, or `iterations` or `parallelism` above 64
  (E-2619).
- A `session.cookieName` that is not a string or names one of the two other
  cookies (E-2552).
- A plugin `id` or first route segment `weakenings` (E-2671).
- A `session.absoluteTimeout` above 400 days (E-2878).

**Behaviour**

- Rate-limit defaults changed: `perIpAddress` is `{ capacity: 30,
  refillPerSecond: 0.5 }` and `perAccount` `{ capacity: 5, refillPerSecond:
  1 / 300 }` (E-2670).
- `session.cookieName` is honoured. If you set it, every signed-in user is
  signed out once (E-2550).
- `beforeSessionRevoke` fires on password changes and sets, resets, identity
  linking and a first address confirmation, and a hook that throws now refuses
  the operation (E-2580, E-2581, E-2730).
- `beforeSignIn`, `afterSignIn`, `beforeSessionCreate`, `afterSessionCreate`,
  `beforeUserCreate` and `afterUserCreate` fire on every way in, not only on
  OAuth, and a hook that throws refuses the sign-in, sign-up, reset or password
  change (E-2790, E-2796).
- `auth.pending.cancel` runs the origin check and the rate limit of its route,
  so a call without an allowed origin is refused with `origin_not_allowed`
  (E-2830).
- Without a configured `log`, weakenings and the default route alarm are
  written to `console.warn` (E-2671, E-2672, E-2674).
- A parameter sent in two sources of one request is refused, a plugin route's
  `redirectToPath` is answered as JSON, an identifier that is not a hyphenated
  uuid names no row, and some plugin migrations are refused (E-2240, E-2241,
  E-2242, E-2483, E-2485).
- `username.change` on an account deleted during the request answers
  `session_required` instead of `invalid_credentials` (E-2835).

**Types** (*Type-level changes* > *Can break compilation*)

- `StartupErrorCode` gains five members, and `RevokeReason` gains
  `email_verified`; an exhaustive `switch` over either stops compiling.
- `HttpEnvironment` requires `sessionCookieName`.
- `PendingNamespace.cancel` requires the call fields, `origin` among them.
- `SessionNamespace` and `PendingNamespace` gain `resolveFromHeaders`, and the
  `user` type of modes `username` and `username_email` gains `findByUsername`;
  an object written by hand against them must supply it.
- The `user` type of mode `username` has no `findByEmail`, and the three removed
  subpaths have no declarations.

## Upgrading from 1.x

1. Change the range to `^2.0.0`. A `^1.0.0` range stays on 1.1.0.
2. Remove any import of the removed `@velve/auth/postgres-js`,
   `@velve/auth/neon` or `@velve/auth/import`. For a driver over `postgres.js` or Neon, write one
   against the driver interface in `DOCUMENTATION.md`.
3. In identity mode `username`, replace `auth.user.findByEmail` with
   `auth.user.findByUsername`.
4. Pass an allowed `origin` and the request's `ipAddress` to every
   `auth.pending.cancel` call.
5. Handle the new members of `StartupErrorCode` and `RevokeReason` in every
   exhaustive `switch`, give a hand-built `HttpEnvironment` its
   `sessionCookieName`, and give hand-written namespace mocks the new members.
6. Start the new version against your configuration once before deploying it.
   A refusal names its code; *Upgrade notes* below says what to do for each.
7. If a plugin implements a sign-in, session, user or revoke hook, check that it
   is ready to run on every path and that a throw now refuses the operation.
8. Decide on rate limits: keep the new defaults or set `rateLimit` explicitly.
9. If you set `session.cookieName`, expect every user to be signed out once.
10. Configure a `log` if the `console.warn` lines are unwanted.

## Upgrade notes: action required

### Five new `VelveStartupError` codes

`VelveStartupError.code` gains five values. Three of them can refuse a
configuration that started on 1.1.0; the other two can be raised only by the
two new options of this release.

| Code | Triggered by | What to do |
|---|---|---|
| `plugin_route_without_address_rate_limit` | A plugin route whose rule, after `rateLimitRules` has applied, has no usable `perIpAddress` bucket: `"none"`, no rule at all, or a `capacity` or `refillPerSecond` that is not a finite number of at least zero. `perAccount: "none"` is still allowed (S-DEFAULT-3, E-2212, E-2214). | Give the route an address bucket, `{ capacity, refillPerSecond }`, in the plugin and in any `rateLimitRules` entry that replaces it. |
| `rate_limit_bucket_unusable` | `rateLimit.perIpAddress` or `rateLimit.perAccount` in the application's configuration is given but is not a real rule with finite capacity and refill rate of at least zero, for example `"none"` passed from JavaScript or through a cast (S-DEFAULT-3, E-2215). | Remove the entry to take the default, or give a real bucket. |
| `plugin_migration_table_not_an_identifier` | A plugin migration's `createsTables` names a table that is not a plain identifier (lowercase letters, digits, `_` and `$`, starting with a letter or `_`, at most 63 bytes), or an element that is not a string primitive (E-2481, E-2482). | Declare each table by its plain lowercase name. |
| `plugin_database_and_role_both_set` | `pluginDatabase` and `pluginDatabaseRole` are both set (E-2642). | Set one of them. |
| `plugin_database_reaches_the_core` | The login `pluginDatabase` connects as is the library's role, can become it or a role that owns the schema, holds `CREATEROLE`, may create objects in the core schema or in `public`, or holds a right on a core table or any of its columns. Raised by `migrate()` and when the check is asked again on a plugin statement (E-2641, E-2646, E-2647). | Create the plugin login as described under *Plugins* > `pluginDatabase` in `DOCUMENTATION.md`. |

### Other refusals at start

These are not `VelveStartupError` codes, but they also stop an instance from
being built:

- `password.argon2id.memoryKiB` above 1048576, or `iterations` or
  `parallelism` above 64, is refused with a `PasswordConfigurationError`
  (`argon2id_memory_above_ceiling`, `argon2id_iterations_above_ceiling`,
  `argon2id_parallelism_above_ceiling`). Before, such a configuration started
  and every password it wrote was then refused (S-DEFAULT-6, E-2619, E-2620).
- `session.cookieName` that is not a string, or that equals
  `__Host-velve_pending` or `__Host-velve_oauth_state`, is refused (E-2550,
  E-2552).
- `weakenings` is now one of the nineteen reserved instance namespaces, so a
  plugin whose `id`, or the first segment of one of its route names, is
  `weakenings` is refused with `plugin_route_conflict` (E-2671).
- `session.absoluteTimeout` above 400 days is refused with an
  `InvalidSessionConfigError` naming the option and the bound. Before, such a
  configuration started and then answered 500 wherever it wrote the session
  cookie, because the cookie's `Max-Age` is derived from the timeout and the
  cookie writer refuses one above 400 days (E-1578, E-2878). A server-side use
  that never writes a cookie can no longer configure a longer timeout either.

### Changed rate-limit defaults

| Bucket | 1.1.0 default | 2.0.0 default |
|---|---|---|
| `perIpAddress` | `{ capacity: 10, refillPerSecond: 0.1 }` | `{ capacity: 30, refillPerSecond: 0.5 }` |
| `perAccount` | `{ capacity: 5, refillPerSecond: 0.01 }` | `{ capacity: 5, refillPerSecond: 1 / 300 }` |

Per route, one address now gets a burst of 30 and then 30 a minute; one account
gets a burst of 5 and then one attempt every five minutes, about 290 a day
whatever the number of addresses (E-2670). To keep the old values, set
`rateLimit` explicitly. An installation that set the old address values
explicitly now logs no weakening for them, and one that set an account refill
between 1 / 300 and 0.01 now logs one where it logged none (E-2670). `DOCUMENTATION.md` gives three presets under
*Rate limiting* > *Recommended presets*.

The default `rateLimit.globalPerRoute.onAlert` was a no-op. It now writes one
`warn` line naming the route, at most once a minute per route and instance,
when a route exceeds `alertThresholdPerMinute` (6000 by default). It still
refuses nothing (S-RATE-8, E-2672). Supply your own `onAlert` or raise the
threshold if the line is noise for you.

### Weakenings are printed when no `log` is configured

Every option set weaker than its default is reported once at start
(S-DEFAULT-1). Without a configured `log` these lines went nowhere. They now go
to `console.warn`, prefixed `[@velve/auth]`, as does the default route alarm;
every other log line still goes nowhere without a sink (E-2671, E-2674). The
only way to silence them is to configure a `log`. Three weakenings that were not
reported before now are: a caller-supplied `fetch`, a longer session idle or
absolute timeout or freshness window, and a raised `refillPerSecond` (E-2210).
The reported list is also available as `auth.weakenings`.

### `session.cookieName` is now honoured

Before 2.0.0 the option was validated and then ignored; the session cookie was
always `__Host-velve_session`. It is now the name written on sign-in, cleared on
sign-out and read on every request (S-COOKIE-1, E-2550). If you set
`session.cookieName`, existing sessions under `__Host-velve_session` are no
longer read after the upgrade, so every signed-in user is signed out once.

### `beforeSessionRevoke` fires in more places, and a refusal now refuses the operation

The hook is now called on a password change or first password set
(`password_changed`), on both password resets (`password_reset`), on identity
linking (`identity_linked`), and on a first address confirmation that removes a
password set in another session, with the new reason `email_verified`
(E-2580, E-2730). On a change, a set, a reset and a first confirmation it runs
inside the operation's transaction, after the account row is locked (E-2705,
E-2733). A hook that throws now refuses the whole operation: the password, the
sessions and a reset's token or recovery code are left as they were (S-OWNER-12,
S-RACE-5, E-2581). A buggy hook can therefore block password changes, resets
and confirmations. Because the hook runs while the account row is held, a slow
hook delays every other credential change, reset and first confirmation of that
account (E-2705).

The context a reset lends its hook runs on the reset's own connection and
refuses every statement once the hook has returned, with
`plugin_lent_connection_returned`. A plugin that keeps that context for later
use gets an error (E-2584, E-2586).

### The sign-in, session and user hooks fire on every way in, and a refusal refuses it

In 1.1.0 `beforeSignIn`, `afterSignIn`, `beforeSessionCreate`,
`afterSessionCreate`, `beforeUserCreate` and `afterUserCreate` were called only
by the OAuth callback, so a plugin that refused a sign-in was bypassed by every
other way in (E-2790). They are now called on:

- **password, passkey and magic-link sign-in:** `beforeSignIn` first, then,
  when the sign-in ends in a session, `beforeSessionCreate`,
  `afterSessionCreate` and `afterSignIn` (E-2790, E-2791);
- **the three second-factor completions** (TOTP, WebAuthn, recovery code):
  `beforeSessionCreate`, `afterSessionCreate` and `afterSignIn`, but not
  `beforeSignIn` again, since the completion is the sign-in its first factor
  began. Every sign-in behind a second factor, an OAuth one included, now
  reaches `beforeSessionCreate` and `afterSignIn` (E-2792);
- **`POST /sign-up` and `POST /sign-up/passwordless`:** `beforeUserCreate`,
  `afterUserCreate`, `beforeSessionCreate` and `afterSessionCreate`, and
  neither sign-in point (E-2793);
- **both password resets, `password.set` and `password.change`:**
  `beforeSessionCreate` and `afterSessionCreate` around the session they issue
  (E-2796).

What a plugin has to expect:

- A hook that throws now refuses these paths with the plugin's code and no
  session is created. A refused sign-up leaves no account; a refused reset keeps
  the old password and leaves its token or recovery code unspent (E-2793,
  E-2796). A throw at `afterSessionCreate` answers with the plugin's code and
  sets no cookie, while the session, and on a reset or change the new password,
  stay (E-2796), except on a sign-up, where `afterSessionCreate` runs inside the
  registration's transaction and a throw rolls back the account and the session
  with it (E-2793).
- `beforeSignIn` runs before any credential is examined and always with
  `userId: null`, for an existing and a missing account alike, so a refusal by
  account belongs at `beforeSessionCreate` (E-2791). A refusal at
  `beforeSignIn` leaves a magic link and a passkey challenge usable.
- A refusal at `beforeSessionCreate` on a second-factor completion keeps the
  pending state, but the TOTP step or the recovery code it was judged on is
  already spent (E-2792).
- On a sign-up `beforeUserCreate` runs once with the identifiers the caller
  sent, before the address is looked up. `afterUserCreate` and both session
  points run inside the registration's transaction, on a connection lent from
  it, so a hook sees the account it is told about and what it writes to its own
  tables rolls back with the registration, except under `pluginDatabase`, whose
  writes go to the plugin login and stay (E-2793, E-2795). That login cannot
  see the account before the registration commits, so under `pluginDatabase` a
  hook's row with a foreign key to `velve.user` for the new account is refused
  with `23503`, the hook throws and every sign-up answers 500 `internal_error`;
  key such a row without that foreign key, or write it after the registration
  has committed, which no sign-up hook does. The same holds for an OAuth
  sign-up's `afterUserCreate`. On a taken address
  the same hooks run on the cover registration, with the address the caller
  sent, and are rolled back with it (S-ENUM-3, E-2793). An OAuth sign-up runs
  `beforeUserCreate` and `afterUserCreate` on a connection lent from the
  callback's transaction in the same way (E-2797). A hook that keeps such a
  context gets `plugin_lent_connection_returned` once it has returned (E-2586,
  E-2795).
- A hook that runs inside a transaction holds it: a slow sign-up hook makes a
  concurrent sign-up on the same address or username wait, and a reset's
  `beforeSessionCreate` runs while the account row is locked (E-2793, E-2796).

### `auth.pending.cancel` takes the call fields and can be refused

`auth.pending.cancel` reached the pending service directly, past the origin
check and the per-address bucket that `POST /pending/cancel` declares, while
3.11 puts both in front of every call, direct server calls included. It is now
the server method of that route (E-2830):

- Its input is `{ pendingToken } & ServerCallFields`, the shape of every other
  method derived from a route, and `origin` is required, so a 1.1 call
  `auth.pending.cancel({ pendingToken })` no longer compiles.
- A JavaScript caller that passes no origin is refused with
  `origin_not_allowed` where it used to succeed, as is one passing a foreign
  origin or `null` (E-2830, E-2831).
- Calls count against the route's per-address bucket, and past it answer 429
  `rate_limited`.

Pass one of the configured origins, as every other server method already asks,
and the request's `ipAddress`. No compatible default exists: 3.11, S-CSRF-1 and
T-CSRF-1 (b) require a server call without an origin to be refused.

### Requests and plugins that relied on lenient handling

- A parameter that arrives in two sources of one request (path, query, body)
  is refused with 400 `invalid_input`, even when both values agree. A client
  that repeats a value, for example `?provider=github` on the callback path,
  must stop (S-OWNER-6, E-2240).
- Only the two OAuth callback routes answer with a redirect. A plugin route
  whose output carries `redirectToPath` now answers that as JSON; do the
  redirect in the application's client (S-REDIR-3, E-2241).
- A session or identity identifier that is not a hyphenated uuid is treated as
  naming no row, so braced or unhyphenated forms that used to reach a row no
  longer do (S-OWNER-8, E-2242).
- A plugin migration not yet applied is refused if it adopts a core table
  through inheritance, changes a core object in place (a constraint, an index,
  a comment), creates a schema, or leaves behind an object such as a
  publication that belongs to none of its tables (E-2483, E-2485).

### PostgreSQL 14 and `pluginDatabase`

If you adopt the new `pluginDatabase` option on PostgreSQL 14, run once:

```sql
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
```

PostgreSQL 15 and newer already ship it this way. Without it every role may
create objects in `public`, and the plugin login is refused with
`plugin_database_reaches_the_core`. The statement affects every role in that
database and may break an application that relied on the old default (E-2646).

### Imported password hashes and memory sizing

The KDF memory bound is now stated against the 64 MiB import ceiling: while
imported credentials above the configured Argon2id memory remain, budget
`concurrentHashLimit × 64 MiB` for derivations, 256 MiB at four places. Each
imported hash moves to the configured parameters at its first successful
sign-in (S-DOS-3, E-2610). A stored Argon2id hash whose memory differs from the
configured value in either direction is now rehashed at sign-in, so lowering
`memoryKiB` rewrites the higher hashes down; they keep verifying until then
(E-2611, E-2621).

## Type-level changes

Taken from the declaration snapshot at `v1.1.0` against 2.0.0. Every change in
the first list is breaking, and they are why the version is 2.0.0 (E-3020).
When this release was prepared as 1.2.0, these notes said strict semver would
call the first five breaking and kept the minor version by the owner's decision
recorded in E-2214 and verified against the declarations in E-2520; the last two
of those five came after E-2520 and are counted in E-2960. The last two entries
of the list are the removals of the major.

Can break compilation:

- `VelveStartupError.code` (`StartupErrorCode`) gains
  `plugin_database_and_role_both_set`, `plugin_database_reaches_the_core`,
  `plugin_migration_table_not_an_identifier`,
  `plugin_route_without_address_rate_limit` and `rate_limit_bucket_unusable`.
  An exhaustive `switch` over it stops compiling.
- `RevokeReason` gains `email_verified`. An exhaustive `switch` in a plugin
  stops compiling until it handles the member.
- `HttpEnvironment` gains the required field
  `sessionCookieName: HostPrefixedCookieName`. Code that builds this object by
  hand for `toWebHandler`, a test harness for instance, must supply it.
- `PendingNamespace.cancel` takes `{ pendingToken: PendingToken } &
  ServerCallFields` instead of `{ pendingToken: PendingToken }`. A 1.1 call
  `auth.pending.cancel({ pendingToken })` no longer compiles, because `origin`
  is required (E-2830); see the upgrade note.
- The instance's namespace types gain required members: `SessionNamespace` and
  `PendingNamespace` gain `resolveFromHeaders(headers: Headers)`, and
  `VelveAuth<M>["user"]` in modes `username` and `username_email` gains
  `findByUsername`. Calling code is unaffected, but an object written by hand
  against these types, a mock in a test for instance, must supply them.
- `VelveAuth<"username">["user"]` has no `findByEmail`. It is
  `UserNamespaceInUsernameMode`, which carries `findById`, `disable`, `enable`,
  `delete` and `findByUsername`; `UserNamespace` keeps its members and is the
  type of mode `email` (E-3022).
- `@velve/auth/postgres-js`, `@velve/auth/neon` and `@velve/auth/import` are
  removed with their empty declarations (E-3021).

Additive:

- `session.resolveFromHeaders(headers)` and `pending.resolveFromHeaders(headers)`
  read the session cookie, under `session.cookieName`, or the pending cookie
  from a `Headers` object and answer as `session.resolve` and `pending.resolve`
  do. Neither checks an origin nor counts against a bucket, by design: a page
  reached by a navigation carries no `Origin` header, and an application that
  authorises a state-changing route of its own with them does its own origin
  check there (3.15 B.2, B.9, E-2832).
- `user.findByUsername({ username })` in modes `username` and `username_email`,
  absent in mode `email`. It looks the name up by the comparison form 3.4 fixes,
  without the configured `UsernameRules`, so an account whose name today's rules
  would refuse is still found (E-2833).
- `VelveAuth<M>["user"]` depends on the mode: `UserNamespace` in mode `email`,
  an interface extending it with `findByUsername` in mode `username_email`, and
  in mode `username` the interface named in the list above. The exported
  `UserNamespace` keeps its members (E-2833, E-3022).
- `VelveAuthConfig` gains `pluginDatabase?: Driver` and
  `pluginDatabaseRole?: string`.
- The instance gains `weakenings: readonly ChosenWeakening[]`.
- `ChosenWeakening`, `{ chosen: string; option: OptionKey }`, is exported from
  the package root.
- On types reachable only through `RouteServices` and the plugin runtime, which
  no entry point exports (E-2520): `SecondFactorCompletion.complete` takes a
  required `presentedSessionToken: string | null`; `SessionService` gains
  `issueReplacingPresented`; `PluginHookDispatcher.beforeSessionRevoke` takes
  an optional second parameter `transaction?: Driver`.
- `VELVE_AUTH_VERSION` is `"2.0.0"`.
- The doc comments in the shipped declarations were rewritten as one plain
  sentence each; no type changed with them (E-1943).

## Security fixes

### Sessions and cookies

- **Every sign-in replaces the presented session (S-FIX-1, S-FIX-3).**
  Password and passkey sign-in, the three second-factor completions, the magic
  link, the provider sign-in and password reset now delete the session row of
  the cookie the request carried, whoever owns it, and insert its successor in
  one transaction. Before, they only inserted (E-2120).
- **A non-string `session.cookieName` is refused (S-COOKIE-2).** Once the name
  reaches the `Set-Cookie` header, an object whose `toString` changes could
  have written a `Domain` attribute (E-2552).
- **An `absoluteTimeout` no cookie can carry is refused at start.** See the
  upgrade notes (E-2878).

### Passwords and timing

- **The background rehash starts after the answer (S-TIM-5).** It used to share
  the event loop with the rest of the sign-in; measured at the median, 66.4 ms
  against 42.5 ms for a current credential, where T-TIM-5 allows 5 ms. It now
  runs in a macrotask after the response is handed back, still inside the KDF
  semaphore (S-DOS-6, E-2150).
- **Concurrent `password.set` and `password.change` (S-FIX-6).** Two calls on
  one account could both succeed: the later commit overwrote the earlier
  credential, so `set` replaced a stored password without the current one, and
  a session the earlier change had revoked was reissued. Now exactly one
  succeeds and the other is refused with 401 `session_required`.
  `revokedOtherSessionsCount` is taken from the rows actually deleted, and
  `beforeSessionRevoke` hears only the sessions the change deletes, once each
  (E-2700, E-2701, E-2705).
- **A malformed identifier on sign-in runs the same lookup (S-TIM-1).** It
  bound `NULL` where every other case bound a string (E-2270).
- **A stored credential the verifier would refuse before deriving is checked
  against the dummy (S-TIM-1, S-TIM-2).** An over-ceiling import, a malformed
  bcrypt string, a short Argon2 salt and similar inputs answered without a full
  derivation, faster than an unknown identifier (E-2616, E-2618).
- **The memory a configured `memoryKiB` above 64 MiB writes is verifiable.**
  Before, every password set under such a configuration never verified
  (E-2615, E-2621). The credential repository refuses to store a credential
  every sign-in would refuse, with `credential_not_verifiable` (E-2617).
- **A semaphore waiter past the wait limit is not granted a freed place
  (S-DOS-4).** A grant after 5003 ms was observed (E-2360).

### Rate limiting

- **The recovery-code reset counts per account and before the KDF (S-RATE-7).**
  Its account bucket was keyed on the identifier as submitted, so each
  spelling of one address had its own bucket, and the new password was derived
  before the bucket was asked. It now uses the comparison form sign-in uses and
  asks the bucket first (E-2180, E-2181).
- **Every weakening is reported, and no route runs without an address limit
  (S-DEFAULT-1, S-DEFAULT-3).** See the upgrade notes for the two new start
  errors and the three weakenings that were silent (E-2210, E-2212, E-2215).

### Input, redirects and randomness

- **A parameter in two sources is refused (S-OWNER-6, E-2240).**
- **Only the OAuth callbacks redirect (S-REDIR-3, E-2241).**
- **A malformed row identifier is answered like one that names no row
  (S-OWNER-8, E-2242).** Before, it answered 500 on revoke and unlink.
- **The cover request's uuid is drawn in the one randomness module (S-RAND-5,
  E-2243).** The type half of S-RAND-6 is not fixed; see *Known limitations*.

### Owner checks

- **Every repository method that reaches rows by owner takes an actor
  (S-OWNER-1).** A static census now enforces it. The password credential
  write, the OAuth identity insert and the OAuth flow insert took a bare user
  id; they now take the actor their callers already held. The one proofless
  password write, used by sign-up, is insert-only, so it cannot overwrite an
  existing credential (E-2420, E-2428, E-2433).
- **A plugin's `revokeSession` deletes under the owner it read (S-OWNER-2).**
  It read the session's owner to announce the revocation and then deleted the
  row by its id alone; the delete now binds that owner in its predicate, and
  the announcement still comes before the row goes. The proof that held this
  as an expected failure now passes (E-2870, E-2941).

### Plugin hooks

- **The sign-in, session and user hooks are called on every way in (3.11).**
  A plugin's veto at `beforeSignIn`, `beforeSessionCreate` or
  `beforeUserCreate` was bypassed by password, passkey and magic-link sign-in,
  by any account with a second factor, by both non-OAuth sign-ups and by the
  password resets. See the upgrade notes (E-2790 to E-2793, E-2796).
- **Sign-up hooks no longer exhaust the pool.** `afterUserCreate` and the
  session points of a sign-up, and the user points of an OAuth sign-up, ran
  inside the registration's transaction on the pool, so a hook could not find
  the account it was told about, and as many concurrent sign-ups as the pool
  has connections, each with a hook that read, answered 500 after the pool's
  wait bound. They now run on a connection lent from the transaction (E-2795,
  E-2797).

### Plugin SQL

- **`pluginDatabaseRole` runs plugin SQL under a database role without rights
  on core tables (S-OWNER-10, E-2450).** The statement check now also refuses
  `set_config` and the functions that run SQL text, such as `query_to_xml`,
  and the role's grants are given one validated table at a time (E-2454,
  E-2456).
- **`pluginDatabase` runs plugin SQL over a second connection that logs in as
  the plugin role (S-OWNER-10, E-2640).** It closes the read of core tables
  that `pluginDatabaseRole` leaves to the statement check. Existing
  configurations are unaffected.
- **Plugin migrations stay off core objects.** The runner reads each declared
  table as one name, and refuses inheritance from or into core tables and core
  objects changed in place (E-2480, E-2483, E-2485).

### Cross-site requests

- **A same-origin read without an `Origin` header is answered (S-CSRF-1,
  S-CSRF-4).** A browser's same-origin `GET` sends `Sec-Fetch-Site:
  same-origin` and no `Origin`, and `GET /session` from the application's own
  page answered 403. A missing `Origin` is now accepted only on the seven core
  reading routes, over the web handler, with `Sec-Fetch-Site` exactly
  `same-origin`; everything else is refused as before (E-2390).
- **`auth.pending.cancel` passes the origin check and the per-address limit
  (S-CSRF-1, 3.11).** Forty direct calls without any origin all succeeded,
  where forty over HTTP from one address met the limit after thirty. A test now
  walks every method of the widest instance with a foreign, a `null` and a
  missing origin, with its exemptions read from the specification (E-2830,
  E-2831).

### Single-use secrets

- **A token or code presented for a disabled account is spent.** The
  recovery-code reset, the mailed reset, the magic link, the address
  verification and the address change refused a disabled account inside the
  transaction that redeemed the secret, so the redemption rolled back and the
  same secret reset the password, signed in, confirmed or moved the address
  once the account was enabled again. Each now commits the redemption and
  refuses after it, with the answer unchanged: the one an invented token or a
  wrong code gets (L-4, S-ENUM-2, E-2872, E-2879, E-2880). A
  rightful owner who uses one while the account is disabled loses it.
- **A TOTP enrolment confirms only the secret its code proved.** An
  `enroll.start` landing between `enroll.finish`'s check and its confirmation
  replaced the unconfirmed secret, and `finish` confirmed the replacement, which
  the user's app did not hold. The confirmation now carries the checked secret
  in its predicate; a `finish` that loses the race answers
  `factor_already_enrolled` if the factor was confirmed meanwhile and
  `invalid_factor_code` otherwise (E-2871).

### Races and error answers

- **Concurrent address changes and OAuth sign-ups give the taken answer.**
  Two accounts confirming a change to the same address at the same time
  answered 500 for the second, where the same redemption without the race
  answers `invalid_token`; it now does (S-ENUM-5, E-2873). Two provider accounts
  with one address signing up at the same time answered 500 for the second; it
  now ends the flow with `oauth_flow_invalid`, as a taken address does, and so
  does a `username` contributed through `identifiersForNewAccount` that another
  account holds (E-2874).
- **`username.change` on an account deleted during the request answers
  `session_required`.** It answered `invalid_credentials`, a code the route does
  not declare (3.15 D.1, B.9, E-2835).
- **A provider's `expires_in` outside 1 second to 365 days is stored as
  `tokenExpiresAt: null`.** A huge value failed the callback with 500, and zero
  or a negative value stored a deadline in the past. The sign-in goes through
  either way (E-2875).

### Revocation announcements

- **The S-LINK-4 sweep is announced with reason `email_verified`.** A first
  address confirmation that deletes a password set in another session revokes
  every session of the account; it now announces each to `beforeSessionRevoke`
  on all three routes that reach it, and a refusing hook rolls the whole
  confirmation back (L-12, E-2730, E-2733).

## Release process

From 2.0.0 the package is published from the maintainer's machine, not from
GitHub Actions, and no registry credential is stored on GitHub (E-2760).
Because npm mints a provenance attestation only from a CI provider's identity
token, 2.0.0 and later versions carry **no** npm provenance attestation.
Every version up to and including `1.1.0` was published from GitHub Actions and
carries one (E-2761). What ties 2.0.0 to its source
is the signed git tag `v2.0.0` on the commit it was published from. Before the
publish, the release tier must have passed on that exact commit, on its push to
`main`; the local sequence refuses a checkout that is not exactly `origin/main`
and cuts the signed tag before publishing (E-2763, E-2765). The sequence is in
`docs/working-method.md` under *Publishing a version*.

## Known limitations

- **Resident memory with `hash-wasm`.** With the optional `hash-wasm`
  accelerator loaded, two hundred simultaneous sign-ins at the default
  parameters raised the resident set by 511 to 966 MiB in nightly runs, against
  T-DOS-3's bound of 384 MiB. After a forced collection it was back within
  20 MiB of where it started, wave after wave, so this is garbage-collection
  lag and not a leak. With `@noble/hashes` alone the rise was about 175 to
  200 MiB and stayed there after collection. T-DOS-3's resident-set threshold
  is not met while `hash-wasm` is loaded; leave headroom beyond the bound
  (`DOCUMENTATION.md`, *Resident set versus memory held*; E-2612, E-2623).
- **A session created during a revocation can go unannounced.** A session a
  concurrent sign-in commits between the listing and the delete of a reset, a
  password set or change, or a first confirmation is deleted without being
  announced to `beforeSessionRevoke` (E-2585, E-2705, E-2730). A set or change
  whose own session is signed out in that same window announces and is then
  refused, so a plugin with effects outside the transaction can hear of a
  revocation that does not happen (E-2705).
- **Revocations no reason names are not announced:** the presented session a
  sign-in replaces, the reissue on a change of trust level, deleting a user,
  and the sweep of expired rows (E-2122, E-2583).
- **A sign-up does not remove the session the browser presented**, and a
  provider answering by `form_post` arrives without the `lax` session cookie,
  so there the presented row stays standing (E-2120, E-2121).
- **With `pluginDatabase`, what a revoke hook writes to its own tables does
  not roll back with the operation** — a reset, a password set or change, or a
  first confirmation, the hook's own refusal included (E-2643, E-2707). The plugin login check asks
  about tables and columns, not core sequences, functions or `SECURITY DEFINER`
  functions (E-2641). The option was exercised against the test connection, not
  with `pg`'s `Pool` (E-2640). The same holds for a sign-up hook's writes when a
  cover registration or a callback rolls back, so a plugin with its own login
  can tell a cover from a registration by what it wrote (E-2795, E-2797).
- **`SignInEvent.userId` is always `null`.** `beforeSignIn` runs before the
  account is known on every path, so the field's type promises a case that
  never happens. A plugin refuses an account at `beforeSessionCreate`, which on
  a magic link comes after the redemption has committed (E-2791).
- **A sign-up cannot be refused by network address.** Neither
  `UserCreateEvent` nor `SessionCreateEvent` carries the caller's address, and a
  sign-up runs no `beforeSignIn` (E-2793).
- **The second-factor method in `afterSignIn` is inferred** from the factors
  the pending row completed, so a future first factor that completes none would
  be reported as `magic_link` (E-2792).
- **`RateAlert.requestsInLastMinute` counts every address check the route has
  taken since the instance started**, not those of the last minute; the field's
  name does not describe it (E-2903).
- **`user.findByEmail` does not fold case**, while `findByUsername` does, so a
  caller who passes a mixed-case address can get `null` for an account that
  exists (E-2833).
- **The WebAuthn counter stores the value last reported**, not the highest
  seen, so a falling counter is reported when it falls. A cloned authenticator
  is reported each time it follows the original, and once the original is no
  longer used the clone is not reported again (E-462, E-2877).
- **L-8's attempt limit holds for sequential guesses only.** It is counted
  after verification, so concurrent guesses against one pending state can
  exceed five (E-2877).
- **G.1's plugin example still does not compile as written**: a `session`
  route's `requestContext.session` is possibly `null`, and the validator it
  uses is exported from no entry point (E-2936).
- **A raised rate limit is reported, not refused.** A refill rate that limits
  nothing starts with a warning (E-2211).
- **S-RAND-6's type half is open.** `CookieWriter.setSession`, `setPending` and
  `SessionService.resolve`, `refresh` and `signOut` still take a plain string,
  so a `SessionId` passes into them without conversion (E-2244).
- **A browser that sends no fetch metadata** (Safari before 16.4) still gets
  403 on a same-origin read without `Origin` (E-2390).
- **The background rehash can be lost** on a platform that stops the process
  once the response is sent, so a stale credential may stay stale (E-2151).
