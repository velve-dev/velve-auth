# @velve/auth 2.0.1

## Summary

2.0.1 is a patch release of 2.0.0. It fixes two bugs and changes nothing else:
no migration, no breaking change, no new configuration, no change to the public
interface. Upgrading is replacing the package; nothing has to be run before or
after it.

## Fixed

### A correct password answered with 401 while another sign-in rehashed it

**Who is affected.** Accounts whose stored password hash is due for a rehash —
a hash imported from another scheme, stored under parameters below the
configured ones, or under an older key version — that sign in more than once at
the same time, on a database driver with a connection pool. That is every real
driver, so two tabs or two devices signing in to such an account at once could
meet it.

**What happened.** The first successful sign-in rehashes the password in the
background after it has answered. That rehash reseals the account's security
state, and the seal's components version moved with it. A second sign-in of the
same account that had already passed its check, and had not yet issued its
session, then inserted no session and answered `401 invalid_credentials` for a
correct password. A retry signed in, since the rehash had finished by then.
T-RACE-6 allows no error for two simultaneous sign-ins (E-3570).

**What changed.** A rehash stores the password the sign-in has just verified
again, so the same password signs the account in afterwards as before. The seal
it writes now keeps the components version, as long as nothing but the
password's hash and key version changed (E-3600). Every other change between a
sign-in's check and its issue still makes the issue come to nothing, as
architecture section 3.18 requires: a password change or reset, a second factor
or sign-in method added or removed, a revocation of every session, a disable the
operator seals and an address change. Section 3.18 states the exception in both
languages.

### A sign-in refused up to about a millisecond before its wait limit

**Who is affected.** Installations under enough load that a password sign-in
waits for a place in the KDF semaphore until its wait limit (S-DOS-4, five
seconds).

**What happened.** The refusal came from a timer, which can fire up to about a
millisecond before as much time has passed by the clock the semaphore measures
the wait on. A waiter could be refused at 4998.9 ms of a 5000 ms limit.

**What changed.** When the timer fires and the wait is still short of the limit,
it sets itself again for what is left, so a refusal happens only once the wait
has reached the limit. A refusal can now come up to one event-loop turn after
the limit instead (E-3571).

## Upgrading from 2.0.0

Install 2.0.1. There is no migration, no configuration to change and no
maintenance step to run. Sessions, open links and pending sign-ins stay valid.

Upgrading from 1.x goes straight to 2.0.1 by the steps in
[the 2.0.0 release notes](./2.0.0.md); nothing is added to them.
