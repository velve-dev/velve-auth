# @velve/auth 1.2.0

## Summary

1.2.0 is a security release. It answers an audit of the security requirements
that found fourteen the code did not, or only partly, satisfied (E-2091), and
the follow-ups that audit led to. Every installation should upgrade. Before
upgrading, read *Upgrade notes* below if any of these applies to you: you run
plugins, you configure `rateLimit` from JavaScript, you set
`session.cookieName`, you implement `beforeSessionRevoke`, you configure no
`log`, or you compile against the exported types with an exhaustive `switch`.
1.2.0 is a minor version by the owner's decision (E-2214, E-2520), although
some of its changes can stop an existing installation from starting.

## Upgrade notes: action required

### Five new `VelveStartupError` codes

`VelveStartupError.code` gains five values. Three of them can refuse a
configuration that started on 1.1.0; the other two can be raised only by the
two new options of this release.

| Code | Triggered by | What to do |
|---|---|---|
| `plugin_route_without_address_rate_limit` | A plugin route whose rule, after `rateLimitRules` has applied, has no usable `perIpAddress` bucket: `"none"`, no rule at all, or a `capacity` or `refillPerSecond` that is not a finite number of at least zero. `perAccount: "none"` is still allowed (S-DEFAULT-3, E-2212, E-2214). | Give the route an address bucket, `{ capacity, refillPerSecond }`, in the plugin and in any `rateLimitRules` entry that replaces it. |
| `rate_limit_bucket_unusable` | `rateLimit.perIpAddress` or `rateLimit.perAccount` in the application's configuration is given but is not a real rule with finite capacity and refill rate of at least zero, for example `"none"` passed from JavaScript or through a cast (S-DEFAULT-3, E-2215). | Remove the entry to take the default, or give a real bucket. |
| `plugin_migration_table_not_an_identifier` | A plugin migration's `createsTables` names a table that is not a plain identifier (lowercase letters, digits, `_` and `$`, starting with a letter or `_`, at most 63 bytes), or an element that is not a string primitive (E-2481, E-2482). | Declare each table by its plain lowercase name. |
| `plugin_database_and_role_both_set` | `pluginDatabase` and `pluginDatabaseRole` are both set (E-2642). | Set one of them. |
| `plugin_database_reaches_the_core` | The login `pluginDatabase` connects as is the library's role, can become it or a role that owns the schema, holds `CREATEROLE`, may create objects in the core schema or in `public`, or holds a right on a core table or any of its columns. Raised by `migrate()` and when the check is asked again on a plugin statement (E-2641, E-2646, E-2647). | Create the plugin login as described under *Plugins* > `pluginDatabase` in `DOCUMENTATION.md`. |

### Other refusals at start

These are not `VelveStartupError` codes, but they also stop an instance from
being built:

- `password.argon2id.memoryKiB` above 1048576, or `iterations` or
  `parallelism` above 64, is refused with a `PasswordConfigurationError`
  (`argon2id_memory_above_ceiling`, `argon2id_iterations_above_ceiling`,
  `argon2id_parallelism_above_ceiling`). Before, such a configuration started
  and every password it wrote was then refused (S-DEFAULT-6, E-2619, E-2620).
- `session.cookieName` that is not a string, or that equals
  `__Host-velve_pending` or `__Host-velve_oauth_state`, is refused (E-2550,
  E-2552).
- `weakenings` is now one of the nineteen reserved instance namespaces, so a
  plugin whose `id`, or the first segment of one of its route names, is
  `weakenings` is refused with `plugin_route_conflict` (E-2671).

### Changed rate-limit defaults

| Bucket | 1.1.0 default | 1.2.0 default |
|---|---|---|
| `perIpAddress` | `{ capacity: 10, refillPerSecond: 0.1 }` | `{ capacity: 30, refillPerSecond: 0.5 }` |
| `perAccount` | `{ capacity: 5, refillPerSecond: 0.01 }` | `{ capacity: 5, refillPerSecond: 1 / 300 }` |

Per route, one address now gets a burst of 30 and then 30 a minute; one account
gets a burst of 5 and then one attempt every five minutes, about 290 a day
whatever the number of addresses (E-2670). To keep the old values, set
`rateLimit` explicitly. An installation that set the old address values
explicitly now logs no weakening for them, and one that set an account refill
between 1 / 300 and 0.01 now logs one where it logged none (E-2670). `DOCUMENTATION.md` gives three presets under
*Rate limiting* > *Recommended presets*.

The default `rateLimit.globalPerRoute.onAlert` was a no-op. It now writes one
`warn` line naming the route, at most once a minute per route and instance,
when a route exceeds `alertThresholdPerMinute` (6000 by default). It still
refuses nothing (S-RATE-8, E-2672). Supply your own `onAlert` or raise the
threshold if the line is noise for you.

### Weakenings are printed when no `log` is configured

Every option set weaker than its default is reported once at start
(S-DEFAULT-1). Without a configured `log` these lines went nowhere. They now go
to `console.warn`, prefixed `[@velve/auth]`, as does the default route alarm;
every other log line still goes nowhere without a sink (E-2671, E-2674). The
only way to silence them is to configure a `log`. Three weakenings that were not
reported before now are: a caller-supplied `fetch`, a longer session idle or
absolute timeout or freshness window, and a raised `refillPerSecond` (E-2210).
The reported list is also available as `auth.weakenings`.

### `session.cookieName` is now honoured

Before 1.2.0 the option was validated and then ignored; the session cookie was
always `__Host-velve_session`. It is now the name written on sign-in, cleared on
sign-out and read on every request (S-COOKIE-1, E-2550). If you set
`session.cookieName`, existing sessions under `__Host-velve_session` are no
longer read after the upgrade, so every signed-in user is signed out once.

### `beforeSessionRevoke` fires in more places, and a refusal now refuses the operation

The hook is now called on a password change or first password set
(`password_changed`), on both password resets (`password_reset`), on identity
linking (`identity_linked`), and on a first address confirmation that removes a
password set in another session, with the new reason `email_verified`
(E-2580, E-2730). On a change, a set, a reset and a first confirmation it runs
inside the operation's transaction, after the account row is locked (E-2705,
E-2733). A hook that throws now refuses the whole operation: the password, the
sessions and a reset's token or recovery code are left as they were (S-OWNER-12,
S-RACE-5, E-2581). A buggy hook can therefore block password changes, resets
and confirmations. Because the hook runs while the account row is held, a slow
hook delays every other credential change, reset and first confirmation of that
account (E-2705).

The context a reset lends its hook runs on the reset's own connection and
refuses every statement once the hook has returned, with
`plugin_lent_connection_returned`. A plugin that keeps that context for later
use gets an error (E-2584, E-2586).

### Requests and plugins that relied on lenient handling

- A parameter that arrives in two sources of one request (path, query, body)
  is refused with 400 `invalid_input`, even when both values agree. A client
  that repeats a value, for example `?provider=github` on the callback path,
  must stop (S-OWNER-6, E-2240).
- Only the two OAuth callback routes answer with a redirect. A plugin route
  whose output carries `redirectToPath` now answers that as JSON; do the
  redirect in the application's client (S-REDIR-3, E-2241).
- A session or identity identifier that is not a hyphenated uuid is treated as
  naming no row, so braced or unhyphenated forms that used to reach a row no
  longer do (S-OWNER-8, E-2242).
- A plugin migration not yet applied is refused if it adopts a core table
  through inheritance, changes a core object in place (a constraint, an index,
  a comment), creates a schema, or leaves behind an object such as a
  publication that belongs to none of its tables (E-2483, E-2485).

### PostgreSQL 14 and `pluginDatabase`

If you adopt the new `pluginDatabase` option on PostgreSQL 14, run once:

```sql
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
```

PostgreSQL 15 and newer already ship it this way. Without it every role may
create objects in `public`, and the plugin login is refused with
`plugin_database_reaches_the_core`. The statement affects every role in that
database and may break an application that relied on the old default (E-2646).

### Imported password hashes and memory sizing

The KDF memory bound is now stated against the 64 MiB import ceiling: while
imported credentials above the configured Argon2id memory remain, budget
`concurrentHashLimit × 64 MiB` for derivations, 256 MiB at four places. Each
imported hash moves to the configured parameters at its first successful
sign-in (S-DOS-3, E-2610). A stored Argon2id hash whose memory differs from the
configured value in either direction is now rehashed at sign-in, so lowering
`memoryKiB` rewrites the higher hashes down; they keep verifying until then
(E-2611, E-2621).

## Type-level changes

Taken from the declaration snapshot at `v1.1.0` against 1.2.0. Strict semver
would call the first three breaking. The version is 1.2.0 by the owner's
decision recorded in E-2214 and verified against the declarations in E-2520.

Can break compilation:

- `VelveStartupError.code` (`StartupErrorCode`) gains
  `plugin_database_and_role_both_set`, `plugin_database_reaches_the_core`,
  `plugin_migration_table_not_an_identifier`,
  `plugin_route_without_address_rate_limit` and `rate_limit_bucket_unusable`.
  An exhaustive `switch` over it stops compiling.
- `RevokeReason` gains `email_verified`. An exhaustive `switch` in a plugin
  stops compiling until it handles the member.
- `HttpEnvironment` gains the required field
  `sessionCookieName: HostPrefixedCookieName`. Code that builds this object by
  hand for `toWebHandler`, a test harness for instance, must supply it.

Additive:

- `VelveAuthConfig` gains `pluginDatabase?: Driver` and
  `pluginDatabaseRole?: string`.
- The instance gains `weakenings: readonly ChosenWeakening[]`.
- `ChosenWeakening`, `{ chosen: string; option: OptionKey }`, is exported from
  the package root.
- On types reachable only through `RouteServices` and the plugin runtime, which
  no entry point exports (E-2520): `SecondFactorCompletion.complete` takes a
  required `presentedSessionToken: string | null`; `SessionService` gains
  `issueReplacingPresented`; `PluginHookDispatcher.beforeSessionRevoke` takes
  an optional second parameter `transaction?: Driver`.
- `VELVE_AUTH_VERSION` is `"1.2.0"`.
- The doc comments in the shipped declarations were rewritten as one plain
  sentence each; no type changed with them (E-1943).

## Security fixes

### Sessions and cookies

- **Every sign-in replaces the presented session (S-FIX-1, S-FIX-3).**
  Password and passkey sign-in, the three second-factor completions, the magic
  link, the provider sign-in and password reset now delete the session row of
  the cookie the request carried, whoever owns it, and insert its successor in
  one transaction. Before, they only inserted (E-2120).
- **A non-string `session.cookieName` is refused (S-COOKIE-2).** Once the name
  reaches the `Set-Cookie` header, an object whose `toString` changes could
  have written a `Domain` attribute (E-2552).

### Passwords and timing

- **The background rehash starts after the answer (S-TIM-5).** It used to share
  the event loop with the rest of the sign-in; measured at the median, 66.4 ms
  against 42.5 ms for a current credential, where T-TIM-5 allows 5 ms. It now
  runs in a macrotask after the response is handed back, still inside the KDF
  semaphore (S-DOS-6, E-2150).
- **Concurrent `password.set` and `password.change` (S-FIX-6).** Two calls on
  one account could both succeed: the later commit overwrote the earlier
  credential, so `set` replaced a stored password without the current one, and
  a session the earlier change had revoked was reissued. Now exactly one
  succeeds and the other is refused with 401 `session_required`.
  `revokedOtherSessionsCount` is taken from the rows actually deleted, and
  `beforeSessionRevoke` hears only the sessions the change deletes, once each
  (E-2700, E-2701, E-2705).
- **A malformed identifier on sign-in runs the same lookup (S-TIM-1).** It
  bound `NULL` where every other case bound a string (E-2270).
- **A stored credential the verifier would refuse before deriving is checked
  against the dummy (S-TIM-1, S-TIM-2).** An over-ceiling import, a malformed
  bcrypt string, a short Argon2 salt and similar inputs answered without a full
  derivation, faster than an unknown identifier (E-2616, E-2618).
- **The memory a configured `memoryKiB` above 64 MiB writes is verifiable.**
  Before, every password set under such a configuration never verified
  (E-2615, E-2621). The credential repository refuses to store a credential
  every sign-in would refuse, with `credential_not_verifiable` (E-2617).
- **A semaphore waiter past the wait limit is not granted a freed place
  (S-DOS-4).** A grant after 5003 ms was observed (E-2360).

### Rate limiting

- **The recovery-code reset counts per account and before the KDF (S-RATE-7).**
  Its account bucket was keyed on the identifier as submitted, so each
  spelling of one address had its own bucket, and the new password was derived
  before the bucket was asked. It now uses the comparison form sign-in uses and
  asks the bucket first (E-2180, E-2181).
- **Every weakening is reported, and no route runs without an address limit
  (S-DEFAULT-1, S-DEFAULT-3).** See the upgrade notes for the two new start
  errors and the three weakenings that were silent (E-2210, E-2212, E-2215).

### Input, redirects and randomness

- **A parameter in two sources is refused (S-OWNER-6, E-2240).**
- **Only the OAuth callbacks redirect (S-REDIR-3, E-2241).**
- **A malformed row identifier is answered like one that names no row
  (S-OWNER-8, E-2242).** Before, it answered 500 on revoke and unlink.
- **The cover request's uuid is drawn in the one randomness module (S-RAND-5,
  E-2243).** The type half of S-RAND-6 is not fixed; see *Known limitations*.

### Owner checks

- **Every repository method that reaches rows by owner takes an actor
  (S-OWNER-1).** A static census now enforces it. The password credential
  write, the OAuth identity insert and the OAuth flow insert took a bare user
  id; they now take the actor their callers already held. The one proofless
  password write, used by sign-up, is insert-only, so it cannot overwrite an
  existing credential (E-2420, E-2428, E-2433).

### Plugin SQL

- **`pluginDatabaseRole` runs plugin SQL under a database role without rights
  on core tables (S-OWNER-10, E-2450).** The statement check now also refuses
  `set_config` and the functions that run SQL text, such as `query_to_xml`,
  and the role's grants are given one validated table at a time (E-2454,
  E-2456).
- **`pluginDatabase` runs plugin SQL over a second connection that logs in as
  the plugin role (S-OWNER-10, E-2640).** It closes the read of core tables
  that `pluginDatabaseRole` leaves to the statement check. Existing
  configurations are unaffected.
- **Plugin migrations stay off core objects.** The runner reads each declared
  table as one name, and refuses inheritance from or into core tables and core
  objects changed in place (E-2480, E-2483, E-2485).

### Cross-site requests

- **A same-origin read without an `Origin` header is answered (S-CSRF-1,
  S-CSRF-4).** A browser's same-origin `GET` sends `Sec-Fetch-Site:
  same-origin` and no `Origin`, and `GET /session` from the application's own
  page answered 403. A missing `Origin` is now accepted only on the seven core
  reading routes, over the web handler, with `Sec-Fetch-Site` exactly
  `same-origin`; everything else is refused as before (E-2390).

### Revocation announcements

- **The S-LINK-4 sweep is announced with reason `email_verified`.** A first
  address confirmation that deletes a password set in another session revokes
  every session of the account; it now announces each to `beforeSessionRevoke`
  on all three routes that reach it, and a refusing hook rolls the whole
  confirmation back (L-12, E-2730, E-2733).

## Other changes

- **Specification.** T-CSRF-1 now names the widest mount, splits the calls it
  makes, and scopes its row count to the rejected calls and to every table
  except `velve.rate_bucket` (E-2731, E-2732). T-CSRF-4 excepts
  `velve.rate_bucket` the same way, because the reading routes are rate limited
  (E-2734). L-12 says the `email_verified`
  announcement comes before the sessions are deleted, not before any row goes
  (E-2733). S-COOKIE-1 and every clause that fixed the session cookie name allow
  `session.cookieName` (E-2550, E-2551). S-CSRF-1 states the same-origin read
  (E-2390). S-DOS-3, S-DEFAULT-6 and S-REST-7 state the amended memory bound,
  the start bounds and the rehash of a memory above the configured one (E-2610,
  E-2611, E-2619, E-2621). A.6 states the new rate-limit defaults (E-2670).
- **Tests.** The weak tests the audit found in the TIM, FIX, ENUM, REPLAY,
  RAND, TOKEN, COOKIE, CSRF, CACHE, KEY, RACE, DEFAULT, DOS, OWNER, LINK,
  REDIR and REST classes were rebuilt over the mounted library (E-2271, E-2302,
  E-2361). New cases drive the concurrent credential changes, the revoke hook
  through every route that announces, and T-CSRF-1 on both paths.
- **Checks.** `pnpm check:decision-refs` fails on a comment in `src/` that cites
  an identifier no document defines. `pnpm check:release-tier` asks whether the
  release tier passed on a given commit (E-2763).
- **Documentation.** Comments in `src/` are one plain sentence each (E-1940,
  E-1943). The complete decision log moved to `docs/decisions/log.md` and
  `CASE-STUDY.md` became a curated selection (E-1972). The README was cut to
  what a first reader needs, with the reference material moved to
  `DOCUMENTATION.md` (E-2030). `DOCUMENTATION.md` documents every option and
  start error above.

## Release process

From 1.2.0 the package is published from the maintainer's machine, not from
GitHub Actions, and no registry credential is stored on GitHub (E-2760).
Because npm mints a provenance attestation only from a CI provider's identity
token, 1.2.0 and later versions carry **no** npm provenance attestation.
Every version up to and including `1.1.0` was published from GitHub Actions and
carries one (E-2761). What ties 1.2.0 to its source
is the signed git tag `v1.2.0` on the commit it was published from. Before the
publish, the release tier must have passed on that exact commit, on its push to
`main`; the local sequence refuses a checkout that is not exactly `origin/main`
and cuts the signed tag before publishing (E-2763, E-2765). The sequence is in
`docs/working-method.md` under *Publishing a version*.

## Known limitations

- **Resident memory with `hash-wasm`.** With the optional `hash-wasm`
  accelerator loaded, two hundred simultaneous sign-ins at the default
  parameters raised the resident set by 511 to 966 MiB in nightly runs, against
  T-DOS-3's bound of 384 MiB. After a forced collection it was back within
  20 MiB of where it started, wave after wave, so this is garbage-collection
  lag and not a leak. With `@noble/hashes` alone the rise was about 175 to
  200 MiB and stayed there after collection. T-DOS-3's resident-set threshold
  is not met while `hash-wasm` is loaded; leave headroom beyond the bound
  (`DOCUMENTATION.md`, *Resident set versus memory held*; E-2612, E-2623).
- **A session created during a revocation can go unannounced.** A session a
  concurrent sign-in commits between the listing and the delete of a reset, a
  password set or change, or a first confirmation is deleted without being
  announced to `beforeSessionRevoke` (E-2585, E-2705, E-2730). A set or change
  whose own session is signed out in that same window announces and is then
  refused, so a plugin with effects outside the transaction can hear of a
  revocation that does not happen (E-2705).
- **Revocations no reason names are not announced:** the presented session a
  sign-in replaces, the reissue on a change of trust level, deleting a user,
  and the sweep of expired rows (E-2122, E-2583).
- **A sign-up does not remove the session the browser presented**, and a
  provider answering by `form_post` arrives without the `lax` session cookie,
  so there the presented row stays standing (E-2120, E-2121).
- **With `pluginDatabase`, what a reset's revoke hook writes to its own tables
  does not roll back with the reset** (E-2643). The plugin login check asks
  about tables and columns, not core sequences, functions or `SECURITY DEFINER`
  functions (E-2641). The option was exercised against the test connection, not
  with `pg`'s `Pool` (E-2640).
- **A raised rate limit is reported, not refused.** A refill rate that limits
  nothing starts with a warning (E-2211).
- **S-RAND-6's type half is open.** `CookieWriter.setSession`, `setPending` and
  `SessionService.resolve`, `refresh` and `signOut` still take a plain string,
  so a `SessionId` passes into them without conversion (E-2244).
- **A browser that sends no fetch metadata** (Safari before 16.4) still gets
  403 on a same-origin read without `Origin` (E-2390).
- **The background rehash can be lost** on a platform that stops the process
  once the response is sent, so a stale credential may stay stale (E-2151).
